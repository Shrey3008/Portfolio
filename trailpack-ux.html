Case study · frontend audit

Auditing a twelve-page frontend, and fixing what the audit found

A pass over every page of TrailPack against how comparable apps handle the same flows — onboarding, checklist UX, empty and error states. Sixteen findings, ranked by impact against effort before any code was written. Eleven shipped, one withdrawn once I measured it, four left open with the reason recorded.

How it was scoped

Audit first, ranked proposal second, code third.

The brief was to improve the UI rather than to fix a named bug, so the first output was not a commit — it was a ranked list of sixteen findings grouped into quick wins, structural work and polish, each with an effort estimate, agreed before implementation started. Every fix then landed as its own reviewable commit with the reasoning in the message.

The net line count is the part I'd point at: 623 added against 1,151 deleted. Most of the value was in removing things that had drifted, not adding features.

Technical highlights

Four pieces worth reading the diff for.

Item 08

Marking the moment a checklist is finished

d25e210

updateProgress() already knew when a list was complete — it used the fact to enable the Start Trip button, then discarded it. Checking off the last item, which is the point of the entire page, produced no acknowledgement beyond a button quietly becoming clickable.

The interesting part is the state, not the animation. It fires on the transition into complete, and the flag starts null rather than false, so the first call after page load only records where things stand. Opening a checklist you finished yesterday stays silent; finishing one while you're looking at it does not. Re-completing after unchecking fires again, deliberately — it is the same moment, and swallowing it would read as a bug.

The toast carries the Start Trip action rather than only applauding, and only when that button is genuinely enabled — so it can never present a dead control.

Item 09

Five loading states became one

68830bf

The app had five loading treatments: skeletons, centred grey “Loading…” text, button spinners, a bespoke discoverLoadingHTML(), and — on two pages — nothing but a console.error. The best of them was walled off: every .tp-skel-* rule carried a body.dash-light prefix, so the only two pages that could show a skeleton were the two that already did.

Moving them to the shared sheet unscoped was the fix, but two details mattered. The skeleton referenced two tokens declared only in the dashboard's own :root, which would have resolved to nothing elsewhere and produced a transparent, borderless card — both now carry fallbacks. And the swap would have regressed accessibility: the grey text was what a screen reader announced, while skeletons are aria-hidden shapes that announce nothing, so a visually-hidden helper went in alongside.

Item 07

CDN failure isolation, then SRI pinning

235f97e · cefe28e

The audit item was “three third-party CDNs”, but the real finding was a failure mode. discover.js called L.map() inside a load handler with no check that Leaflet had arrived. When unpkg is blocked, the ReferenceError escaped the handler and took the render function with it — so a failed map did not merely lose the map, it blanked the entire Discover section below it. The map is optional; the content is not.

Leaflet already carried integrity hashes. html2pdf and Chart.js did not, so two unpinned third-party scripts were executing with full page privileges. Hashes were computed from the pinned versions, confirmed stable across two separate fetches, then loaded in a browser with the attribute set to prove neither hash blocks the script. 

html2pdf.bundle.min.js   884 KB   cdnjs      now pinned
chart.umd.min.js         200 KB   jsDelivr   now pinned
leaflet.js                        unpkg      already pinned
Items 13 / 14

Error states that name the cause

adf2e1a · 564474f

The largest element above the fold on the checklist page rendered its full layout with every reading replaced by an em-dash — six dashes, a placeholder glyph and a five-day forecast strip of nothing — whenever weather could not be resolved. One failure path served every cause, so it could never say which had happened. A card that renders the shape of information it does not have reads as broken rather than as empty.

The trigger in practice was a blocked geolocation permission, whose rejection fell through to a generic catch that could not distinguish it from a network error. It is now caught where it happens and split by error code, because only one of the three is permanent: 

1  PERMISSION_DENIED      permanent   → "Add a location"
2  POSITION_UNAVAILABLE   retryable   → "Use my location"
3  TIMEOUT                retryable   → "Use my location"
   no destination on trip             → "Add a location"
   lookup failed for a known place    → "Try again"

That distinction is the whole point. Once a browser has blocked a site after repeated dismissals, calling getCurrentPosition() again does nothing — so offering a retry button for code 1 would be a control that cannot work, which is the same class of problem as the em-dash skeleton: UI that looks functional and isn't. Codes 2 and 3 are transient and get a real retry; code 1 gets the action that works without location at all, and the browser-settings route described in prose rather than dressed as a button.

Following that thread surfaced a second gap. The “Add a location” action had nowhere to go — nothing in the frontend could set an existing trip's location, because the only location input lived in the create-trip modal. The backend had accepted location, lat and lon on its update route the entire time; only the UI never asked. The existing editor grew the missing field rather than gaining a second one.

Not yet verified end to end. The save round-trip has never been run — whether the request succeeds, whether the re-fired lookup then resolves, and whether the panel flips from “Location blocked” to a live forecast. The modal renders and the script parses; that is what has been checked, and it is recorded as an open flag in the commit message rather than left implied.

The finding I withdrew

Item 04 — measured, disproved, removed from the plan.

I flagged the Sign In button on the login page as failing contrast: in a screenshot it rendered a washed-out green that read as disabled rather than primary. It was in the ranked plan as a fifteen-minute quick win.

Measured against the rendered page, it was the intended #2d6a4f at full opacity. The screenshot compression was pale, not the CSS. No change was made, and the item is recorded as withdrawn rather than quietly dropped — an audit that only ever confirms its own findings isn't an audit.

A debugging aside

Diagnosing a network failure that wasn't one.

Mid-session, git push began failing instantly — not timing out — against github.com. My first two explanations were both wrong, and the way they were wrong is the useful part.

  • First theory: the hotspot's upstream had dropped. DNS resolved, Wi-Fi was up, a default route existed, but every host failed in ~3 ms. Wrong — I had sampled only failing hosts.
  • Second theory: a local content filter or VPN blocklist. Because cloudflare.com answered in 0.16 s while GitHub and Vercel refused instantly, and GitHub and Vercel are exactly what this project deploys through — a suspicious pairing. Also wrong.
  • Actual cause: IPv4 was dead; IPv6 was fine. The same host over both protocols settled it — cloudflare.com returned 301 over IPv6 and failed over IPv4. Cloudflare wasn't whitelisted, it simply publishes AAAA records. GitHub and Vercel publish none, so they were IPv4-only, and IPv4 was the broken path. A carrier hotspot on an IPv6-only network with NAT64 that had stopped synthesising addresses.

The lesson I'd keep: the deciding test was the one that held the host constant and varied the protocol. Both wrong theories came from comparing different hosts and reading meaning into which ones failed.

Still open

Four items, all blocked on the same thing — an authenticated session on the deployed app.

10 · Hero/chip overlap at 800px

The action cluster overlaps the metadata row at one viewport width. Confirmed present before this work started — pre-existing, not a regression.

11 · Eight inline :root blocks

The stylesheet half of the token consolidation is done. The inline half sits mostly on pages that need a session to render, so changing them blind would mean editing CSS nobody can look at.

12 · Two pages with no loading state

Not inconsistent styling — the absence of any. Both fetch then populate, with failures going only to console.error, so tables are indistinguishable from a genuinely empty result until data lands.

15 · Destination stores no coordinates

Item 14's field sets the location string but not lat/lon, so weather geocodes the text rather than using stored coordinates — accurate for real place names, useless for anything unmappable.

The largest single change was f3fb4c0: a 1,000-line stylesheet that no page loaded, and which two test files wrongly asserted was loaded. Of its 56 class selectors, 46 targeted classes appearing in no markup, and eight of its eleven keyframes duplicated animations the codebase already implemented under better names — moving them would have added a sixth copy of spin. Three had no equivalent and were kept; the rest went.
